Three Architecture Approaches for Dime

Choose the foundation — everything else builds on this decision

A

Structured Monolith + Celery/Redis

One Python service with internal module boundaries. FastAPI handles REST + WebSocket. Celery runs ADK agent tasks in the background. Redis is both the Celery broker and the real-time pub/sub channel to the Svelte UI.

Svelte UI ←→ FastAPI (REST+WS) ←→ PostgreSQL
                         ↓
                  Redis (broker)
                         ↓
             Celery Workers (ADK agents)
                         ↓
             compendium/ + art/ + signal

Pros

  • Simplest deployment
  • Fastest to develop locally
  • Redis already in stack
  • Single codebase, easy refactor

Cons

  • Celery adds operational weight
  • Harder to scale workers independently
  • Redis less suited for complex routing
B

API + Worker Split with RabbitMQ ★ Recommended

Two services, one message broker. dime-api (FastAPI) handles all UI communication. dime-worker (ADK agents) consumes tasks from RabbitMQ and writes results back. Both live in the same repo, separate containers — same machine locally, split to Cloud Run + GKE in production.

Svelte UI ←→ dime-api (FastAPI+WS) ←→ PostgreSQL
                         ↑↓
                RabbitMQ (tasks+events)
                         ↑↓
             dime-worker (ADK agents)
                         ↓
             compendium/ + art/ + signal

Pros

  • RabbitMQ is your turf
  • Natural local/cloud split seam
  • Worker can scale independently
  • Priority queues, dead letters, retries
  • Multiple workers in parallel

Cons

  • Two services to run locally
  • More moving parts than option A
  • RabbitMQ container overhead
C

GCP-Native with Cloud Tasks + Pub/Sub

Lean fully into Google Cloud. Cloud Tasks handles scheduling and queueing. Cloud Pub/Sub handles events and real-time updates. ADK workers run as Cloud Run Jobs. No broker to operate yourself.

Svelte UI ←→ Cloud Run (FastAPI) ←→ Cloud SQL
                         ↑↓
          Cloud Tasks / Cloud Pub/Sub
                         ↑↓
         Cloud Run Jobs (ADK workers)
                         ↓
            GCS / compendium/ + signal

Pros

  • Fully managed, no broker ops
  • Native GCP scaling
  • Tight ADK integration
  • Pay-per-use in production

Cons

  • Hard to run locally without emulators
  • Vendor lock-in
  • Local dev experience suffers
  • Overkill until you need scale

My recommendation: B. RabbitMQ is already in your mental model, it gives you real queue semantics (priority, routing, dead-letters) that matter for agent pipelines, and the API/worker split is the natural seam you'll need when you go to cloud. Local dev is docker compose up — one extra container is worth the payoff.
